# 时间导演功能重规划报告（只读调查，不改代码）

日期：2026-09-10。对象：`koishi-plugin-hds-interlude` 时间导演（timeline director），0.1.5 引入至今。数据源：Koishi Desktop 生产实例全部日志（2026-08-11 → 09-10）+ 源码 `service.ts:3558`、`narrator.ts:443`、`script/timeline-routing.ts`。

## 1. 现状事实

| 指标 | 数值 |
| --- | --- |
| 计费调用总次数（全日志） | 182 次（09-03 单日 106 次） |
| 成功次数（"已生成事件账本"） | **0** |
| 拒绝原因分布 | 100% "返回不是 JSON 对象"（即解析层拿不到任何 JSON） |
| 输出 token 分布 | 大量聚集在 523-548（超过代码里的 max_tokens=480）；另有 1/8/57 的近空输出 |
| 输入 token | 5,419 - 22,690/次 |
| 连锁后果 | 导演失败 = 该次自动推进整体丢弃。09-03 单日 141 次"未生成有效账本/已熔断" |

**最重要的损害**：`needsTimelineDirector`（timeline-routing.ts）对 `advance` 恒为 true——即**每一次自动推进都硬依赖时间导演**。0% 成功率意味着生产实例上自动生活流实质瘫痪：故事只能靠用户消息轮次推进，长时段被压进单次追赶剧本（09-10 凌晨那句"星期三的大半个白天几乎都在昏睡中掠过"就是游标卡了一整天后的补写）。同时每次失败都白烧 API（09-03 约 70 万输入 token）。

顺带指出一处**文档与实现不符**：service.ts:219 注释声称熔断后"自动推进降级为无账本守恒推进"，实际代码（:3683）是 `return succeeded:false`——熔断后推进被冻结，没有降级路径。

## 2. 根因分析（按证据强度排序）

1. **输出预算被思考吃掉/截断**：导演请求 `max_tokens: 480`，模型是 yunwu 上的 gemini-3.7-flash（思考型）。输出计量 523-548 > 480，说明网关把 thinking 计入输出——JSON 在中途被截断，或思考吃光预算导致可见内容为空（日志里的 1/8 token 输出）。这是"返回不是 JSON 对象"的最直接解释。
2. **网关不强制 JSON**：`response_format: json_object` 在 yunwu/gemini 转发下未必生效，模型可以自由输出散文。
3. **任务-提示词错配**：系统提示词以 `KNOWLEDGE_WRITING_FRAME`（原文写作框架）开头——这是给主叙事写散文用的框架，而任务只要 4 条极简 JSON beat。模型被"写作框架"引导，倾向开始写叙事而非吐 schema。
4. **输入过重**：近期条目 12×800 字、contactThreads 全文、最近剧本全文、召回历史——5-22k token 的输入对一个输出 ≤480 token 的结构任务严重过量，既慢又贵还稀释指令权重。
5. **诊断盲区**：解析失败在 narrator 内部 catch，原始输出只记 debug 级且不上抛；service 只拿到 undefined，warn 里永远是"原始返回=null"。182 次失败没有留下一次模型真实返回的样本——这就是"从来没有成功过却一直不知道为什么"的直接原因。

## 3. 这个功能到底应该干什么（重新定位）

主叙事在自动推进时要一次跨越 40 分钟到数小时的生活窗口。时间结构——先做什么后做什么、何时被打断、睡多久、几点醒来看到几条消息——目前全靠主叙事的散文即兴，这正是时间越界、跳过未来日程、睡眠时长失真的来源。时间导演的正确定位：

> **在主叙事写作之前，用极低成本先产出这个窗口的相对时间骨架（1-4 个 beat），让主叙事去渲染骨架，而不是发明时间。**

它从四个方面提升拟真度：

1. **作息连续性**：睡眠、通勤、课表/工作块在窗口内有显式先后，不因换窗重置；
2. **消息感知时点真实**：夜里发的消息，beat 显式锚定"at 07:10 醒来，看到 3 条未读"，而不是模型即兴决定她半夜秒回或睡死不看；
3. **长窗口时间守恒**：到期意图和日程块是约束不是许可——不提前完成未来的约定；
4. **主叙事效率**：骨架定了，散文只渲染，减少越界重写（也就减少了上一节"结构化回复缺失"这类长输出诱发的失败）。

## 4. 性能重规划建议

- **输入瘦身**：导演只需要结构信号——当前场景钩子、日程块、due intents（type+notBefore）、最近 3-5 条的 kind+时间戳、上一窗口的账本/carry。砍掉近期条目全文、contactThreads、最近剧本全文。目标输入 <1.5k token（现在 5-22k，**约 1/10 成本**）。
- **输出预算**：480 → 1500+，或对该路由关闭思考/低推理档；beat summary 限 60 字。
- **独立路由**：不再挂 compaction 通道；这是小结构任务，任何 fast/cheap 模型可胜任。可分层：**规则先行**（作息表+日程块直接生成确定性 beats）**模型兜底**（只有规则覆盖不了的窗口才调用）——多数夜间睡眠窗口根本不需要模型。
- **失败降级链（关键）**：解析失败 → 规则骨架兜底 → 都不行才冻结窗口；同时把 rawText 带到 warn 日志（修盲区）。熔断后应降级为无账本守恒推进（与注释声称一致），而不是冻结——冻结是当前最大的现实损害。
- **频率**：每次 advance 至多一次导演调用；<20 分钟、同日、无日程边界的窗口维持现有豁免；熔断 2h 冷却保留。

## 5. "看不见消息不入事件"会不会睡死

**结论：机械上不可能睡死，风险不在醒不来，而在醒来的时机不真实。**

机制核查（源码事实）：
- "没条件看见就不当事件"**不是机械门**——代码里没有任何一处会丢弃或延后用户消息。消息总是立即入库并调度一个 user-message 写作轮（`needsTimelineDirector` 对 user-message 恒 false，完全不受导演成败影响）。"看不见"是叙事层的：剧本写她睡着，模型在她醒来时才安排"看到"。今晨 05:29 的语音就是实例——她在被窝里被写醒、抓手机回复，轮次是即时发生的。
- 三重唤醒保证：(a) 任何用户消息强制触发一轮写作；(b) 自动推进在 rest window（23:00-07:00）只是放慢到 120-240 分钟间隔，**从不停**；(c) urge 调度照常跑。所以"推进不知道要睡多久"不成立——推进每 2-4 小时必然叫醒一次。

真正的问题是**叙事睡眠时长与推进窗口脱节**：剧本写她睡 8 小时，但推进 2 小时就到点，模型只能压缩睡眠或硬醒——这正是时间导演该管的场景。导演修好后，beat 可以显式写 `at 0.0 入睡`、`at 0.85 醒来看到 N 条未读`，主叙事照此渲染，睡眠时长与推进窗口物理对齐；跨夜窗口还可以由规则层（作息表）直接产出确定性 beats，零模型成本。

## 6. 建议的验收标准（供下次实施用）

1. 连续 3 天日志中"已生成事件账本"> 0 且拒绝率 < 10%；
2. 导演单次输入 < 1.5k token、输出完整可解析（无 480 截断特征）；
3. 熔断状态下自动推进仍以规则骨架继续（日志不再出现连续"保留时间窗口等待重试"堆积）；
4. 夜间消息在剧本中的"看到时点"落在作息醒来时间附近（±30 分钟）而非随机。
