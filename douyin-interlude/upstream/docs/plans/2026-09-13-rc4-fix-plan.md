# rc4 补充修复计划（2026-09-13）

> 基于 rc3 审计报告，按影响面排序。全部属于功能衔接修复，不扩大主提示词、不改变剧本化核心。

## 一、补充事实 lastSeenAt 缺失导致检索崩溃 — P0

### 问题
rc2/rc3 修复了 ID 和 status，但创建补充事实时没有写 `lastSeenAt`。`facts()` 排序执行 `fact.lastSeenAt.getTime()`，空值直接抛 `Cannot read properties of null`。启用记忆且有补充事实时，**普通对话的事实检索可能失败**。

### 改动点

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/service.ts` | `createStory` 补充事实 dbCreate (~L1185) | 加 `lastSeenAt: now` |
| `src/service.ts` | `facts()` 排序 (~L8408) | 空值兼容：`(fact.lastSeenAt ?? fact.updatedAt ?? fact.createdAt).getTime()` |
| `src/service.ts` | 补充事实写入后 | 补一条迁移：对已有 `lastSeenAt: null` 的补充事实补填（按 `createdAt` 回填） |

### 验收
- [ ] 新建故事后 `lastSeenAt` 非空
- [ ] rc2/rc3 写入的旧记录不崩溃（空值兼容路径）
- [ ] `facts()` 排序对 null 值不抛错
- [ ] 补充事实参与检索且出现在 `durableFacts` 载荷中

### 改动点

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/service.ts` | `persistDecision` 内 `isAgencyCheck` 分支 (~L4184) | 把 interaction 合成从"Commit 后"移到 Commit 构建之前（与 advance 的合成预检同位置），使 commit-builder 正常生成事件绑定 |

具体：在 `decisionToScriptCommit` 调用前，当 `isAgencyCheck && decision.proactiveContact && !decision.interaction?.reply?.content` 时，从 `authoredActions` 合成 interaction 并注入 decision。

### 验收
- [ ] proactive-check 回合的合成消息有 scriptEvent 绑定
- [ ] `deliveryReality` 不报 `no-outgoing-action-recorded`
- [ ] 分段投递的确认/失败正常更新账本

## 三、管理员注记与最新原始剧本的预算共存 — P1

### 问题
注记保护先保留全部 admin-note，再用剩余预算选普通剧本。两条 7K 注记可把最新原始剧本完全挤出 12K 预算窗口——触碰"不能丢失原始剧本"的核心。

### 改动点

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/narrator.ts` | `compactPromptEntries` (~L1947) | 给 admin-note 保护加预算上限：最多保留 N 条最新注记（建议 3 条 × 2,000 字 = 6,000 字），超出部分退化为截断保留首句。确保原始剧本始终有 ≥50% 预算（≥6,000 字）可用 |

具体逻辑：
```ts
// admin-note 保护上限：最多 3 条、每条截断至 2,000 字、总占预算 ≤6,000 字
const adminProtected = entries.filter(e => e.kind === 'admin-note').slice(-3)
const adminBudget = Math.min(6000, adminProtected.reduce((s, e) => s + e.content.length, 0))
// 剩余预算 ≥ budget - adminBudget 用于普通剧本
```

### 验收
- [ ] 2 条 7K 注记 + 1 条最新剧本：注记保留（可能截断），剧本也保留
- [ ] 10 条短注记 + 大量剧本：注记保留，剧本保留
- [ ] admin-note 前缀仿写测试（普通用户写 `[管理员注记]` 在 user-message 条目中不触发管理员语义——因 ownership 是 user-delivered-message 而非 system-event）

## 四、侧端健康上报真正接通 — P2

### 问题（三层）

1. 注册 reporter 时 `this.narrator` 尚未创建 → 条件分支不执行
2. 侧端任务仍调旧 `sideTaskJson()` 而非新 `sideTaskJsonWithHealth()`
3. reporter 参数不匹配 `(task, ok)` vs `(ok)`
4. compactor 是单独实例，只给 narrator 注册不覆盖 compactor

### 改动点

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/narrator.ts` | `sideTaskJson` (~L398) | **不新增 wrapper**——直接在 `sideTaskJson` 的 try/catch finally 中调用 `this.onSideTaskHealth`。消灭调用入口分裂问题 |
| `src/service.ts` | narrator 创建后 (~L745) | 把 reporter 注册移到 `this.narrator = createNarrator(...)` **之后**（而非内联在同一行之前） |
| `src/service.ts` | compactor 创建后 | 同样给 `this.compactor` 注册 reporter |

### 验收
- [ ] 压缩/导演/Preplan/Overlay/Alter 的成败都计入 `sideTaskTotal`/`sideTaskFailed`
- [ ] reporter 参数签名一致

## 五、主动联系"成功"计数改到发送结果后 — P2

### 问题
当前在把消息加入 `messages` 数组时就 `recordProactive(story.id, true)`——此时还没得到平台发送结果。

### 改动点

| 文件 | 位置 | 改动 |
|---|---|---|
| `src/service.ts` | crossActions 投递点 (~L4269) | 删除加入数组时的 `recordProactive(true)` |
| `src/service.ts` | `sendOutgoingMessages` 的回调/确认处 | 在实际投递确认后（`confirmOutgoingDeliveries` 或投递成功回调）调用 `recordProactive(storyId, sent)` |

最小可行方案：把 `recordProactive` 移到 `sendOutgoingMessages` 返回结果判定处——有 `delivered` 则 `true`，否则 `false`。

### 验收
- [ ] 主动联系成功只在平台确认后计数
- [ ] 白名单拦截/网络失败不计成功

## 六、Token 按故事归属 + 幻觉检测拓宽 — P3

### Token 归属
把 `canonicalStoryIdForHealth` 从"上一次成功叙事的 storyId"改为从 `TokenUsageRecord` 自身携带的上下文获取（如给 record 加可选 `storyId` 字段，由各调用方填充）。最小改动：在 `recordNarrativeComplete` 时同步更新 `lastActiveStoryId`（已有），但把初始值从 `undefined` 改为**当前 canonical story 的 ID**（在 `constructor` 中初始化）。

### 幻觉检测
在现有"电话号码"检查外，增加：**未被提供的具体人名**——`/[^你她他我它]\w{1,3}(说|问|回复|发来)/` 匹配模型编造的第三方发言行为。
