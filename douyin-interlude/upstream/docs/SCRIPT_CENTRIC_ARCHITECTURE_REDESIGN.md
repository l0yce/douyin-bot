# HDS Interlude 高度剧本化架构重设计

状态：历史目标架构提案，已分阶段实施；并非所有目标均已验收。当前 `1.0.1-rc6` 的实际边界以 [当前架构](ARCHITECTURE.md)、[V2 实施表](V2_IN_PLACE_REFACTOR_IMPLEMENTATION_FORM.md)、[更新记录](CHANGELOG.md) 和 [beta7 证据关系与分段修复报告](development/BETA6_EVIDENCE_DELIVERY_REPAIR.md) 为准。  
基线版本：`0.1.5-beta10-foresight`  
目标：在不削弱 HDSI 剧本中心思想的前提下，解决当前真实感提升不明显、功能链路失效、状态学习停滞和主提示词负担过重的问题。

## 1. 不可动摇的中心思想

HDSI 不是问答机器人，也不是在角色扮演外壳中运行的聊天助手。它首先是一段持续发生的生活剧本。

用户消息只是进入这段生活的一个外部事件。主角是否听见或看见、当时在做什么、有没有条件回应、回应前发生了什么、是否选择沉默、回复了什么，以及回复后生活如何继续，都必须由同一次剧本推进共同决定。

因此，本设计采用以下不可违背的原则：

1. **剧本是唯一叙事真相。** 已提交的剧本不是展示层，也不是为了包装回复而生成的附属 prose，而是人物生活、关系和后续因果的事实来源。
2. **消息是剧本事件的一个子类型。** 不存在脱离剧本的“聊天决策器”或“回复生成器”。
3. **一次推进必须原子化。** 场景推进、人物行动、内在反应、消息行为和状态变化共同构成一个不可拆分的 `ScriptCommit`。
4. **可见消息必须直接来自剧本。** 平台发送的文字必须与剧本中的消息事件逐字相同，不能在剧本之外再次改写、润色或重新判断。
5. **允许自然不回复。** 沉默、没看见、晚些回复、只看了一眼和打字后放弃，都应当是完整的剧本结果，而不是回复模块的失败。
6. **持续性高于单轮完整性。** 每轮是长篇连续剧本的一段，不是一篇自成一体的新短篇，也不需要为了形式完整而补足固定篇幅。

这六条构成 HDSI v2 的架构验收门槛。任何使消息脱离剧本单独决策的实现，即使能提高短期回复质量，也不应进入主链路。

## 2. 当前架构真正的问题

当前问题不是“剧本化太强”，而是剧本生成的结构和持久化方式没有真正围绕连续剧本建立。

### 2.1 剧本长度被误当成剧本密度

beta10 固定要求实时回合写出 400–700 字，并要求每次像一篇新的作品。这会带来三个偏差：

- 几分钟甚至几十秒的现实窗口也被迫填充成完整段落；
- 模型把注意力用在凑足场景形态、转折和收束，而不是忠实延续正在发生的生活；
- “每次都是新作品”与连续生活、稳定人物习惯和未完成场景直接冲突。

高度剧本化不等于每轮都要有固定的文学篇幅。真正需要约束的是事件密度、因果完整性和时间覆盖，而不是字数。

### 2.2 输出虽然同时包含剧本与回复，数据模型仍把它们视为两个平行结果

当前 `script` 和 `interaction.reply` 在协议上是两个字段。提示词要求它们一致，但数据库、拆分发送、节奏统计和失败处理又分别操作它们。由此产生隐性分叉：

- 剧本描述了一次发送，平台投递却可能失败；
- `<sep/>` 拆分后只留下多条短消息，丢失原始整轮结构；
- 后续模块可能学习消息记录，也可能学习剧本 prose，两者缺少统一事件身份；
- 修复回复时可能只重新生成互动字段，没有重新生成导致它的场景因果。

这不是足够彻底的剧本中心结构。消息不应只是与剧本并排返回的字段，而应当是剧本事件账本中的一项。

### 2.3 状态层不是剧本的可靠投影

当前大量功能把状态保存在同一个可选字段很多的 `story.state` JSON 中，再经过手写归一化函数反复复制。只要某个字段未被归一化函数显式保留，功能就会在重载后静默消失。ChatRhythm 即属于这种情况。

continuity、facts、memory、workingDetails、Overlay、Perspective、Alter、场景在场表和投递摘要又分别保存相近信息。它们不是从同一剧本事件账本稳定派生的视图，因此容易出现：

- 某层知道一件事，另一层不知道；
- 旧摘要覆盖新状态；
- 临时情绪进入长期人格候选；
- 配置已经启用，但已有故事没有对应持久化字段；
- 模块生成了结果，却没有在下一轮重新进入主剧本。

### 2.4 当前“学习”没有理解剧本中的发展

自由字符串路径的 `statePatch` 要求模型反复使用近似相同的路径和措辞，才能累计到应用门槛。人物发展在自然语言中往往会换一种说法，因此候选被切碎；而偶然重复的临时状态反而可能被误判为稳定变化。

真正的剧本式学习不应从一轮回复是否像上一轮出发，而应追踪：

- 什么事件改变了人物；
- 人物如何在多个场景中重复表现这种变化；
- 变化是暂时反应、关系限定习惯，还是稳定人格演化；
- 后来的剧本是否提供了反证；
- 变化在哪些场景条件下成立。

### 2.5 主提示词承担了过多异质职责

当前 system prompt 同时包含世界观原则、时间守卫、隐私、记忆解释、阶段策略、消息格式、贴图规则、文学风格、反重复规则和结构化输出协议。大量负面例子还会成为模型反复联想到的语言锚点。

问题不是提示词不够强，而是主模型看到的不是一份清晰的“续写任务”，而是一份不断增长的系统规章汇编。

## 3. 新的核心抽象：ScriptCommit

v2 不再以“模型回复”作为一次运行的产物，而以 `ScriptCommit` 作为唯一产物。

一个 `ScriptCommit` 表示：从上一个故事游标到本轮终点，这个世界中实际发生的一段连续剧本。

建议的概念结构如下：

```ts
interface ScriptCommit {
  id: string
  storyId: string
  phase: 'live' | 'advance' | 'due' | 'follow-up'
  window: {
    start: string
    end: string
  }
  prose: string
  events: ScriptEvent[]
  developmentEvidence: DevelopmentEvidence[]
  continuityDelta: ContinuityDelta
  status: 'pending-delivery' | 'committed' | 'committed-with-delivery-failure'
}
```

`ScriptEvent` 是剧本内部可寻址的事实节点：

```ts
type ScriptEvent =
  | IncomingMessageEvent
  | PerceptionEvent
  | ActionEvent
  | InternalShiftEvent
  | OutgoingMessageEvent
  | DeliveryOutcomeEvent
  | SceneTransitionEvent
  | PromiseEvent
  | RelationshipEvent
```

每个事件至少拥有：

- `eventId`：稳定身份；
- `sceneTime`：发生时间；
- `actor`：事件主体；
- `causedBy`：直接因果来源；
- `evidence`：依赖的既有剧本事实；
- `content`：该类型允许的内容；
- `visibility`：用户可见、叙事可见或仅系统记录。

`prose` 与 `events` 不是两套互相竞争的真相。事件是同一段剧本的结构化索引，prose 是它的完整叙事表达。二者必须在一次模型生成中共同产生，并由验证器检查一致性。

### 3.1 消息如何嵌入剧本

当主角回复消息时，模型应当在剧本事件序列中产生 `OutgoingMessageEvent`：

```ts
interface OutgoingMessageEvent {
  kind: 'outgoing-message'
  eventId: string
  sceneTime: string
  actor: string
  causedBy: string[]
  participantId: string
  content: string
  bubbles: string[]
  deliveryIntent: 'send-now' | 'send-later'
}
```

平台发送 `bubbles` 中的原文。它不再读取另一个 `interaction.reply`，也不对文本做二次创作。

如果没有 `OutgoingMessageEvent`，本轮就没有可见回复。这意味着不回复是剧本选择，而不是缺失字段。

### 3.2 消息事件必须有剧本因果

每个可见消息事件必须能回溯到同一提交内或既有账本中的因果链，例如：

```text
用户消息进入世界
  → 手机在可接触范围内
  → 主角在某个时刻注意到提示
  → 当前活动和情绪产生反应
  → 主角决定拿起手机并组织措辞
  → outgoing-message 事件
  → 生活继续或被消息改变
```

这条链不要求每一步都写成长段心理描写，但不能由宿主在剧本之外补做“是否回复”的判断。

## 4. 统一的高度剧本化运行流程

### 4.1 第一步：把外部输入写成剧本事实

用户消息到达时，宿主先把它写成 `IncomingMessageEvent`。它是现实进入故事的事件，不是对 assistant 的指令。

这一事件应保留：

- 实际接收时间；
- 用户明确提到的事件时间；
- 来源参与者和关系分支；
- 原始内容及允许的媒体观察；
- 引用、回复和群聊上下文；
- 投递渠道事实。

### 4.2 第二步：编译“可续写剧本上下文”

上下文编译器不替模型决定剧情。它只把现有剧本整理成一份有优先级、有来源、不过载的续写材料：

1. 上一个故事游标附近的连续原始剧本；
2. 当前场景、地点、活动、在场人物和设备可达性；
3. 当前时间窗口与确定性日程边界；
4. 与本次事件直接相关的既有剧本片段；
5. 人物稳定发展、关系状态和 Perspective；
6. 尚未闭合的承诺、行动和情绪余波；
7. 当前进入世界的外部事件。

检索应区分“内容相似”和“文风相似”。长期检索以事件摘要和证据索引为主，只有命中后才附带少量原始剧本。这样保留剧本权威性，同时避免把大量相似 prose 反复喂回模型，形成自我模仿。

### 4.3 第三步：主模型续写完整 ScriptCommit

主模型仍是唯一的场景作者。它在同一次推理中决定：

- 时间窗口内发生了什么；
- 外部消息何时以及是否被主角感知；
- 人物活动是否被打断；
- 人物的动作、想法和情绪如何变化；
- 是否形成消息事件；
- 消息原文和气泡边界；
- 场景最后停在哪里；
- 哪些内容可能构成人物发展证据。

主模型不需要先填写一个独立聊天策略，再根据策略写回复。所有这些都由续写同一段剧本时共同完成。

### 4.4 第四步：验证整个剧本提交，而不是单独修复回复

验证器只执行现实性和协议性检查，不替作者作语义决定：

- 所有事件是否位于时间窗口内；
- 消息是否先于其感知或发送条件出现；
- 人物是否拥有相关设备、隐私和行动能力；
- prose 中的可见消息是否与事件内容一致；
- 是否虚构用户已经说过或确认过的事实；
- 状态变化是否有剧本证据；
- 是否越过确定性日程和场景边界。

若消息与剧本矛盾，应重试整个 `ScriptCommit` 的相关场景段，而不是只补一个回复字段。局部重试也必须携带原始事件序列和矛盾说明，返回一个新的完整提交版本。

### 4.5 第五步：通过事务型 Outbox 投递剧本中的消息

为避免“剧本说已发送，但平台实际失败”，应采用事务型 Outbox：

1. `ScriptCommit` 与其中的 `OutgoingMessageEvent` 一起保存为 `pending-delivery`；
2. Outbox 按事件 ID 投递完全相同的气泡内容；
3. 成功后写入 `DeliveryOutcomeEvent(delivered)`，提交转为 `committed`；
4. 失败后写入 `DeliveryOutcomeEvent(failed)`，提交转为 `committed-with-delivery-failure`；
5. 下一轮剧本把失败视为世界中真实发生的技术事件，而不是假装消息已经到达。

拆分气泡只是一个消息事件的运输投影。数据库必须保留拆分前的完整事件及 bubble 顺序，ChatRhythm 一类模块不得再从逐条投递记录反推整轮结构。

## 5. 长短时间窗口的剧本推进

### 5.1 实时窗口

实时窗口不能再根据时间间隔切换剧本精细度。无论两次事件相隔数秒还是数分钟，人物动作、感知、语言和因果关系都使用同一叙事分辨率。时间只规定“这段窗口里来得及发生什么”，不规定“应该写得多细”。

过去按时间缩放精细度的方案，在高密度对话中会形成危险的反馈链：窗口越短，剧本越倾向于压缩和省略；省略后的剧本又成为下一轮上下文和学习材料；模型随后会把上一次的压缩性误差当成事实继续推演，最终让语言、动作和情节产生加速偏移。实时系统必须从数据结构上切断这条链，而不是继续调节时间阈值。

#### 固定 SceneFrame

每个活动场景维护一个不可被普通消息随意重写的 `SceneFrame`：

- 地点、在场人物和视角位置；
- 主角正在进行的活动、姿态和可支配注意力；
- 设备可达性与隐私条件；
- 当前关系气氛和即时情绪基线；
- 尚未完成的动作、话题和场景线索；
- 本场景采用的叙事焦距、语言密度和描写习惯。

SceneFrame 在场景建立时确定。后续高密度消息持续复用同一个 frame，只有真实的场景转换、动作完成、外部事件或有证据的状态变化才能修改它。模型不得因为“又来了一条消息”就重新概括地点、重设姿态、切换文风或重新解释人物情绪。

叙事分辨率只允许在有明确剧本原因的场景边界上变化，例如从课堂转入放学路途、从群体活动转入独处，不能由两条消息之间经过了多少秒决定。

#### 只追加 SceneDelta

实时推进生成的是相对于当前 SceneFrame 的 `SceneDelta`，而不是重新生成、摘要或改写已经提交的场景：

```ts
interface SceneDelta {
  frameId: string
  startsAfterEventId: string
  events: ScriptEvent[]
  proseAppend: string
  frameChanges: EvidenceBoundFrameChange[]
}
```

`proseAppend` 只能描述新发生的部分。已提交剧本保持不可变，下一轮也不得用新的措辞复述上一轮事件来替代原文。这样，高密度对话只会让同一场景增加更多细小但完整的事件，不会让旧情节被重复转述后逐轮变形。

篇幅由本轮新增事件的数量和复杂度自然产生，但每个事件的语义精度保持稳定。只有一条消息事件时，总篇幅可以较短；这表示新发生的事情较少，而不是采用了更粗糙的描写模式。

#### 对话突发段 DialogueBurst

同一场景中连续发生的密集消息构成一个 `DialogueBurst`。它不是独立聊天会话，而是 ScriptCommit 内一组共享 SceneFrame、话题状态和语言惯性的剧本事件。

在一个 burst 内：

- 每条用户消息仍然是独立的 `IncomingMessageEvent`；
- 每次感知、停顿、动作和回复仍按发生顺序追加；
- 主角的用词和语气从同一人物状态连续演化，不为每条消息重新初始化；
- 不重复生成场景背景，不把省略背景误认为背景已经改变；
- 没有新因果来源时，不引入新的支线、配角行动或环境转折；
- burst 的结束以叙事焦点或场景状态发生变化为准，空闲时间只能作为触发整理的工程信号，不能反向定义剧本内容。

#### 新情节准入必须有因果锚点

实时窗口内的新剧情不能由模型为了“让这一轮有内容”而自由补充。任何新的情节 beat 至少引用一种因果锚点：

1. 当前进入世界的外部事件；
2. 已提交但尚未完成的动作自然完成；
3. 已确认的日程或环境边界到达；
4. 当前场景中已经积累到足以产生变化的条件；
5. 宿主提供的真实外部观察。

没有锚点时，只能继续当前动作、对话、注意力变化或情绪余波。所有 `frameChanges` 和新 beat 都必须保存 `causedByEventIds`，验证器拒绝无来源的地点变化、人物出现、活动切换和情绪跃迁。

#### 实时连续性与长期学习隔离

实时剧本可以立刻更新当前场景物化视图，使下一条消息知道人物刚刚做了什么、说了什么；但它不能在每个高密度回合后立即改写长期人格、关系或 DialogueHabitProfile。

长期学习改为场景检查点机制：

1. 实时回合只记录带事件 ID 的候选 `DevelopmentEvidence`；
2. 同一 DialogueBurst 内的重复表达先聚合，不按消息条数重复加权；
3. 场景结束、焦点转换或稳定检查点到达后，统一审查整段剧本；
4. 同一场景对同一发展维度最多贡献一次有效权重；
5. 学习器同时读取支持证据和反证，不把模型对自身上一轮 prose 的复述视为新证据；
6. 场景原文保持可检索，但长期发展只从去重后的剧本事件证据晋升。

这使高密度对话能够保持即时连续性，却不会因为一分钟内出现十条消息，就获得相当于十个独立生活场景的学习权重，从而避免人物特征和情节倾向被指数式放大。

实时窗口的最终流程为：

```text
读取固定 SceneFrame
  → 追加新的外部事件
  → 主模型生成同分辨率 SceneDelta
  → 校验新事件、因果锚点和 frameChanges
  → 不可变地追加到 ScriptCommit
  → 更新即时场景视图
  → 到场景检查点后再做一次长期学习归并
```

### 5.2 长时间后台推进

较长空档仍然必须高度剧本化，但可以采用同一作者链路的分层生成：

1. 先生成 `BeatSkeleton`，只标记时间段、主要活动、转折和消息接触机会；
2. 宿主校验时间与日程边界；
3. 主模型依据同一 skeleton 渲染完整 `ScriptCommit`；
4. outline 与 prose 一起提交，不能让另一个独立模型生成互不相干的世界事件。

短实时回合不使用时间导演。长间隔 outline 失败时，应缩小窗口或退化为保守的连续生活，而不是冻结整个故事游标。

## 6. 剧本驱动的人物发展系统

### 6.1 DevelopmentEvidence 取代自由 statePatch

人物发展必须来自已提交剧本中的具体事件：

```ts
interface DevelopmentEvidence {
  subject: string
  dimension:
    | 'preference'
    | 'habit'
    | 'relationship'
    | 'boundary'
    | 'value'
    | 'communication-style'
    | 'world-belief'
  scope: 'global' | 'relationship' | 'situation'
  claim: string
  evidenceEventIds: string[]
  direction: 'support' | 'contradict'
  strength: number
}
```

模型可以提出证据，但不能发明路径，也不能直接修改人物档案。宿主按受控维度聚类，保存支持、反证、跨场景次数和最近更新时间。

### 6.2 三层人物变化

人物状态应明确分成：

1. **即时状态**：疲惫、烦躁、兴奋、忙碌；随场景自然衰减；
2. **关系限定模式**：只在面对某位参与者时形成的称呼、玩笑方式、戒备或亲近；
3. **稳定发展**：跨时间、跨场景反复成立的偏好、习惯、价值观和人格变化。

即时状态不能仅凭重复措辞升级为稳定人格。重大剧情事件可以提高单次证据权重，但必须记录其事件来源。

### 6.3 对话习惯仍属于剧本人物，而不是聊天子模型

原 ChatRhythm 应重构为 `DialogueHabitProfile`。它描述人物在剧本中的消息行为，不独立生成或决定回复。

学习单位是拆分前的完整 `OutgoingMessageEvent`，并保留场景条件：

- 当时活动与可用注意力；
- 情绪和关系状态；
- 消息行为属于解释、安慰、调侃、敷衍还是主动分享；
- 气泡数、总长度、停顿和标点；
- 是否在消息后继续生活动作。

它向主作者提供的是历史分布和角色习惯，例如“忙碌时多为一条短回复，放松且主动分享时常拆成两至三条”，而不是“本轮必须改成三个气泡”。

风格变化必须有衰减和上下文条件，不能设置永久粘性的 `exhausted` 熔断。

## 7. 现有模块在新架构中的位置

| 现有模块 | v2 定位 |
| --- | --- |
| recentScript | 保留，作为连续续写的第一上下文；增加稳定事件 ID |
| continuitySnapshot | 改为从事件账本派生的当前场景物化视图 |
| facts | 改为带剧本证据 ID 的长期事件与事实索引 |
| memory 表 | 删除，或并入剧本 Episode 索引，不再保留无明确写入协议的平行记忆层 |
| workingDetails | 并入当前场景和开放线索，不再形成泛化杂项袋 |
| ChatRhythm | 由 DialogueHabitProfile 取代，读取完整消息事件 |
| Alter | 保留为剧本情绪惯性；只从已提交事件累计并进入下一次续写 |
| Perspective | 保留为人物看待世界的稳定层；增加已有故事迁移 |
| Overlay | 改由 DevelopmentEvidence 聚类晋升，禁止自由路径补丁 |
| Agency Window | 作为主作者的现实边界和提交验证器，不在剧本外单独决定是否回复 |
| Schedule Preplan | 作为未来场景约束，不当作已发生事件 |
| 时间导演 | 仅作为长时间空档的同链路 outline；实时回合移除 |
| delivery summary | 由带结果的消息事件和 Episode 索引取代 |

Alter 不能被宣传为人物学习模块。它只是人物状态在连续场景间的低频惯性。人物是否变得更信任某人、形成新习惯或改变边界，应由 DevelopmentEvidence 负责。

## 8. 主提示词重写方案

主提示词应从“规章总表”改成“连续剧本作者协议”。建议固定部分只保留以下层级。

### 8.1 第一层：叙事本体

- 你是持续生活剧本的作者，不是聊天助手；
- 当前输入是进入世界的新事件；
- 续写从故事游标开始，到权威终点停止；
- 消息只能作为剧本中的人物行动出现；
- 不得为了回答用户而跳过人物当时的生活和现实条件。

### 8.2 第二层：不可违反的现实边界

- 权威时间窗口；
- 当前地点、活动、在场者；
- 设备、隐私、日程和行动能力；
- 用户明确确认的外部事实；
- 不可跨越的世界边界。

边界应以结构化事实提供，避免在固定提示词中堆积大量负面案例。

### 8.3 第三层：人物与连续性

- Canon；
- 当前场景；
- Perspective；
- 已证实的发展；
- 当前 Alter；
- 关系限定行为；
- 与本事件有关的原始剧本片段。

### 8.4 第四层：当前续写任务

只描述本轮 phase、时间跨度、新进入的事件和必须闭合或继续保持开放的线索。不同 phase 使用独立短模块，不把所有阶段规则同时放入 system prompt。

### 8.5 第五层：ScriptCommit 协议

模型必须返回完整 prose 和可寻址事件；任何 outgoing message 都必须存在于 prose，并且文字、顺序和气泡边界一致。

应删除以下固定条款：

- 每个实时回合必须 400–700 字；
- 每段必须自成一体；
- 把每轮当成全新作品；
- 刻意改变上一轮的形状；
- 大量列举“不要再出现某某情节”的反例；
- 脱离事件条件的统一回复长度和气泡要求。

反重复不应靠要求作者忘记连续性，而应靠上下文去重、情节状态、人物习惯分布和评测发现。

## 9. 持久化重构

建议从单一大 JSON 状态迁移为事件源与物化视图并存：

### 9.1 权威表

- `interlude_script_commit`：一次完整剧本提交；
- `interlude_story_event`：可寻址的剧本事件；
- `interlude_delivery_outbox`：待投递消息事件；
- `interlude_delivery_outcome`：平台投递结果；
- `interlude_development_evidence`：人物发展证据；
- `interlude_character_model`：由证据计算出的当前人物发展；

### 9.2 物化视图

- 当前场景；
- 人物即时状态；
- 关系状态；
- 开放承诺与线索；
- Episode 索引；
- DialogueHabitProfile；
- Schedule 和 Agency 能力窗口。

所有物化视图都必须可以从带版本的权威事件重建。不能再因为某次 `normalizeStoryState()` 漏拷字段而永久丢失功能状态。

### 9.3 兼容策略

迁移期保留现有 `interlude_script_entry` 作为兼容投影，但新主链只写 `ScriptCommit` 和 `StoryEvent`，再由投影器生成旧格式记录。待控制台、查询和压缩路径全部完成迁移后，再移除双写。

## 10. 代码结构建议

当前 `service.ts` 和 `narrator.ts` 承担过多职责。v2 建议按剧本生命周期拆分，而不是按零散功能继续增加 helper：

```text
src/script/
  context-compiler.ts       编译连续剧本上下文
  contract.ts               ScriptCommit 与 ScriptEvent 协议
  author.ts                 唯一主剧本生成入口
  validator.ts              时间、因果、能力和文本一致性验证
  commit-store.ts           原子提交和版本控制
  projection.ts             recentScript、场景和兼容记录投影
  delivery-outbox.ts        消息事件投递与结果回写
  development.ts            剧本证据聚类和人物发展
  dialogue-habits.ts        剧本内消息习惯的条件分布
  episode-index.ts          剧本事件检索与原文片段回取
```

`service.ts` 最终只负责 Koishi 生命周期、队列和调度；`narrator.ts` 不再容纳所有模型任务和提示词拼装。

## 11. 不应继续补丁式维护的部分

下列内容不建议在原结构上继续增加开关或提示词补丁：

1. 为 ChatRhythm 补一个遗漏字段后继续沿用逐条投递统计；
2. 给自由 statePatch 增加更多字符串别名；
3. 为 memory 表再增加一句“请记忆重要事项”；
4. 给时间导演增加更多重试，却仍让它处理短实时回合；
5. 继续向主 system prompt 添加反重复例子；
6. 用更多字数规则制造“剧本感”；
7. 在 `interaction.reply` 与 `script` 之间继续添加一致性补丁；
8. 在大 `story.state` 归一化函数中不断手工补字段。

这些修复会延长旧数据模型的寿命，却不会建立以剧本事件为唯一真相的架构。

## 12. 分阶段实施清单

### 阶段 A：定义和测量

1. 冻结 beta3、beta10 作为回放基线；
2. 定义 `ScriptCommit`、事件类型、因果关系和投递状态；
3. 建立真实剧本回放集；
4. 增加功能闭环追踪：生成、验证、持久化、重载、投影、下一轮消费；
5. 记录主模型实际使用的 provider、endpoint、model 和协议模式。

### 阶段 B：当前主链渐进替换

1. 实现事件账本和 ScriptCommit store；
2. 实现上下文编译器和新的剧本作者提示词；
3. 沿当前唯一主链依次替换状态编解码、内部 ScriptCommit、正向提示框架和事件输出；同一轮不得由 v1、v2 并行生成；
4. 使用冻结输入和数据库副本做离线顺序回放，比较连续性、因果、消息自然度、沉默合理性和成本；
5. 完成 Outbox 投递及失败回写。

### 阶段 C：切换主链

1. v2 ScriptCommit 成为唯一生成结果；
2. 平台只投递其中的 OutgoingMessageEvent；
3. continuity、事实和开放线索改从事件投影生成；
4. 实现 DialogueHabitProfile 与 DevelopmentEvidence；
5. 为 Perspective、Alter 和现有关系状态执行一次性迁移。

### 阶段 D：删除旧架构

1. 删除独立 `interaction.reply` 主路径；
2. 删除旧 ChatRhythm；
3. 删除自由路径 statePatch；
4. 合并空置 memory 表和重复摘要层；
5. 删除实时回合的时间导演；
6. 移除大 JSON 状态的旧字段和兼容投影。

## 13. 评测标准

HDSI 的评测不能只看“回复像不像人”，还必须看消息是否真正属于剧本。

### 13.1 剧本—消息耦合

- 每条可见消息都能追溯到同轮感知、行动和场景条件；
- 删除消息事件后，剧本因果链应出现明显缺口；
- 单独拿出消息时不能表现为脱离生活状态的万能问答；
- 消息内容与 prose 逐字一致；
- 平台失败后，后续剧本不得假设对方已经收到。

### 13.2 连续生活质量

- 时间窗口覆盖合理，不凭空填充；
- 场景位置、活动、人物在场和设备条件连续；
- 自动推进不是围绕等待用户消息展开；
- 未完成动作和情绪可以自然延续，不强制每轮收束；
- 长间隔有生活变化，短间隔不会制造过量剧情。

### 13.3 人物发展

- 稳定变化均有剧本事件证据；
- 临时情绪不会直接写入永久人格；
- 关系限定习惯不会泄漏到所有参与者；
- 对话结构随场景变化，同时保持可识别的人物习惯；
- 后续反证能够削弱或撤销旧结论。

### 13.4 工程闭环

- 每个功能状态在持久化、重载后仍存在；
- 每个生成字段都有明确消费者；
- 每个进入提示词的状态都能追溯来源；
- 不存在长期为零、无生产者或无消费者的数据表；
- 集成测试覆盖“生成 → 提交 → 投递 → 重载 → 下一轮续写”。

## 14. 最终取舍

本设计不通过削弱剧本来提高聊天质量，也不建立一个独立的回复大脑。

它要改变的是：从“生成一段 prose，再附带一个回复字段”，升级为“提交一段带事件身份、因果、时间和投递结果的连续剧本”。消息仍然只是人物生活中的一个事件，但这个事件会被可靠地保存、投递、学习和带入下一段生活。

HDSI 与普通角色聊天机器人的边界不在于每轮写了多少字，而在于：角色不是在等待问题后生成回答；角色一直生活，而消息只是在合适的时刻进入并改变这段生活。
