## 大问题：暂不自动修改

### P1-A：重置、暂停与后台任务缺少统一的失效标识

- 代码依据：`service.ts` 的 `scheduleCompaction` 将模型调用放到串行队列外；回到 Phase 3 时主要检查瞬时 `databaseResetting`，而 `setDesktopRuntimePhase` 的暂停主要撤销定时器。
- 风险：后台请求开始后执行 purge，等清空结束、标志复位，旧模型结果才返回；或暂停时模型正在生成，结束后仍继续保存/投递。群聊本次增加了局部屏障，后台整理等任务仍需要统一处理。
- 证据级别：静态时序风险，本次日志未证明发生过旧记忆回写。
- 建议：每个故事使用任务代次；重置递增代次，提交前校验。暂停需明确是“停止新任务”还是“也停止在途投递”，分别处理落库与外部发送，不能只扩展一个布尔开关。
- 验收：模拟压缩/预排/主写作在途 purge、暂停及恢复，确保旧结果不会复活，新消息不被误删，已发送消息不能被误报为未发送。

### P1-B：前台优先只保护尚未开始的后台工作

- 代码依据：`advanceStory` 的 serial 包围 `advanceUnlocked`，其中包含主模型调用；手动整理 `compactUnlocked` 也存在长任务持有队列的路径。排队整理虽然已分成读/模型/写三个阶段，但它不是所有调用路径的统一约束。
- 风险：后台先开始时，新用户消息的串行保存/快照仍可能等待长模型调用。反过来，前台生成在队列外时，强制手动推进与其重叠也需要提交版本保护。
- 证据级别：代码结构确认，尚无本次端到端延迟测量。
- 建议：逐步统一“短锁读快照 → 无锁模型调用 → 短锁校验提交”，引入游标/版本冲突检测；不能仅移除 serial，否则会变成覆盖剧情状态。
- 验收：自动推进开始后立刻收私聊/群音频，测接收和排队延迟，并核对最终只有一个一致的故事游标。

### P1-C：JSON 故障恢复把多种失败混为同一种处理

- 实际证据：9 月 16 日多次压缩 invalid JSON/timeout，另有主叙事结构恢复仍失败。
- 代码依据：`narrator.ts` 的 `sideTaskJson` 将部分 invalid JSON/empty response 归为疑似思考预算截断，Chat Completions 下移除 max_tokens 重试；时间导演/压缩/预排等取首个提供商，与主叙事多提供商恢复不同。
- 风险：格式错误不一定是截断；取消输出上限可能增加耗时和费用，却不能恢复结构。仅凭现有日志不能归因到具体网关返回形态。
- 建议：先记录脱敏的失败阶段、finish_reason、实际模型/协议/预算和有限文本样本，再区分截断、空响应、结构缺字段、网络错误；所有恢复受单任务总预算约束。是否提供后台备用路由需要配置语义设计。
- 验收：覆盖正常 JSON、带围栏、截断、错误正文、空响应和缺字段；验证有限尝试次数、费用累加及成功后记忆检查点推进。

### P1-D：音频能力与提供商健康尚未分离

- 代码依据：Anthropic 明确拒绝原生音频，而主模型通用 failover 将请求异常按提供商失败处理并设置冷却。
- 风险：纯文本正常的 Messages 连接，会因“不支持音频”的确定性能力问题被重复尝试、进入冷却。没有配置兼容备用时，音频回合仍不能完成。
- 证据级别：可确定的路由机制冲突，未将它归因到本次日志中的具体失败。
- 建议：明确声明/识别原生音频能力，在请求前选取兼容路由；能力不匹配不影响文本健康。不做自动转写或丢弃音频来伪装成功。
- 验收：Messages + 音频兼容备用、只有 Messages、关闭 failover 三种组合，确认路由透明、无无意义重试，后续文字回合不受污染。

### P2-E：群音频强制写作还缺批次级资源策略

- 代码依据：群消息逐条调用 `loadNativeAudio`；已有单消息附件数和单文件大小限制，但合并批次没有总字节/总附件限制，群 debounce 也会随新消息重置。
- 风险：持续刷群时触发被不断推后；一次合并大量音频又可能显著增加内存、请求体与模型开销。
- 建议：保留“音频必触发”的目标，用最大等待时间和分批消费保障接收，不静默截断或丢弃。总预算应与模型输入能力、排队上限一起设计。
- 验收：连续文字夹音频、多个大音频、加载失败与持续高频消息，验证有限等待、每条附件最多消费一次及未处理附件的可追踪性。
